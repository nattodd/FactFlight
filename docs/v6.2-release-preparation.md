## Two-tab investigation — release blocked

The previously intermittent two-tab test was rerun with synthetic learners and tracing of family-store writes. It reproduced actual lost updates: each tab wrote a complete family record containing only its own newly created learner, and both tabs subsequently read a final record containing only one learner. This is not explained by an assertion running before both UI actions completed. No real learner data or personal browser was accessed.

The shared `update(change)` routine performs a whole-record localStorage read/modify/write inside `navigator.locks.request`. This routine is byte-for-byte identical to v6.1 production. Thus the inspected write path predates the voice changes; this investigation does not prove all deployed browsers exhibit the issue. The exact browser scheduling/cache mechanism has not been proven, at the time of that investigation. The local safeguard below now prevents competing updated tabs from writing.

The failure demonstrates loss of a synthetic learner during concurrent creation. Other operations use the same write helper, so their concurrent safety cannot be assumed from this result. It does not establish that the owner's saved history has been lost. The initial successful isolated rerun was insufficient to close the concern.

**Local fix — single saving tab:** each page requests an exclusive Web Lock at initialization and holds it until page exit. Other pages fail closed for learner creation, rename, delete, import and flight saving; a persistent warning explains the restriction. Reads, exports and Guest practice remain available. Failed flight saves retain the existing unsaved/export path. The page does not automatically take over: export unsaved results, close the saving tab, then reload the other tab. Page-history restoration also requires reload before writing. Multiple store instances within the saving page share ownership and perform synchronous read/change/write operations. No schema, storage key, migration, arbitrary delay or voice change was introduced. Existing lost records cannot be reconstructed by this safeguard.

This deliberately trades simultaneous saving for data safety. Close old-version tabs before testing or releasing: older code does not implement the lifetime ownership policy. The original 13/15 outcome remains historical evidence, not a passing result. New tests assert explicit rejection and unchanged data, unsaved export, close/reload recovery, simultaneous page initialization, and refusal of every mutation in the non-saving tab. Required physical-browser checks remain open.
