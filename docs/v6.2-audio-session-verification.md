2026-11-16. Local uncommitted follow-up to `406d301` on `v6.2-development`. No commit, push, merge, deployment or Netlify change.

## Findings and scope

The owner confirms Chrome is identified as using the microphone after completion/backgrounding/lock and that Home navigation no longer clears it. The parent restriction passed. The previous cleanup did not pass physical testing.

WebKit's source shows an inactive recognizer ignores abort, while the Audio Session API offers a separate native category override. The [research and implementation record](v6.2-microphone-privacy-verification.md#audio-session-follow-up--2026-11-16-local-only) links primary sources and distinguishes this candidate from a verified hardware fix.

The app now requests `ambient` on terminal/background cleanup where the iOS Audio Session API is available, and requests `auto` before preparing the next voice flow. It retains the existing shutdown gate, natural endings, cue and 400 ms cooldown; it does not change categories between answers to a non-recording category. A generation check prevents an older shutdown continuation from changing a newer session. Missing or throwing Audio Session APIs do not crash or disable ordinary fallback. Desktop never writes the audio-session category.

The ended-object abort workaround is removed. The recognition mock now ignores abort after natural end rather than treating that call as a hardware-release success. Diagnostic version `voice-lifecycle-diagnostics-3-audio-session` records bounded event/category/state observations and iOS audio-end events, without transcripts or learner data. A category request does not change the reported state in the mock: tests explicitly preserve and report `active` rather than inventing a release.

## Physical checks still required

**Owner result on `ccc1c41`: failed release verification.** The amber microphone indicators persist after completion/backgrounding Chrome and locking/unlocking. The owner observes that the orange dot disappears during microphone preparation between answers. Home/backgrounding cleared the indicators once, but another attempt needed reopening Chrome and backgrounding it again without selecting anything. This intermittent behavior is not a pass. The observation suggests comparing the synthesis transition with terminal cleanup; it does not establish that synthesis causes release. No further application change is included in this result record.

On both iPhone Safari and Chrome, start with a browser session whose microphone indicator is already clear. Complete a short voice flight, remain on Results, background for 30 seconds, lock/unlock and inspect both the amber indicator and Control Center. Return and complete another voice flight. Also check cancel during setup, background/reconnect during a question, and parent restriction followed by deliberate re-enabling.

The native release gate remains open until those checks pass. `ambient` requests a non-recording category; it is not a supported JavaScript command to force the OS microphone off, and an AudioSession state alone is not proof of capture ownership. No real microphone, permission prompt or OS-level release was tested here. If the category change is unsupported or ineffective on the target device, this candidate must not be represented as resolving the privacy issue.
